Machines

Use a home server, an old laptop, a Codara Cloud box or a throwaway sandbox as extra compute. Agents and Cora workers run there; their terminals, files, ports and previews show up in Studio as if they were local. The full plan is docs/machines-plan.md.

How it fits together

Studio already opens projects over SSH, forwards dev server ports, and reaches Cloud boxes through a proxy. A machine is any of those connections, shown in one list. Work runs over there; only the screen comes back here.

One Machines list

Every place compute can come from is one row: status, CPU, RAM, disk, load, and the agents running there. Numbers come from one tiny command every 10 seconds (about 5 ms). Inside containers it reads the real limits: a probe in a 1 CPU / 1 GiB container otherwise reports the host's 24 CPUs and 31 GiB.

Add a machine

  1. SSH host or alias from ~/.ssh/config, or user@host.
  2. Tailscale name, like nas.tail1234.ts.net. Nothing extra to install in Studio.
  3. Codara Cloud box, from the existing picker.
  4. Pair through the relay for a machine behind NAT: a later option, not planned now.

What goes on the machine

First release: nothing. Studio uses the machine's own shell, its own agent CLIs and tmux if present, so agents survive Studio closing. Later: codara-host, a small signed helper Studio uploads itself (the machine never downloads code on its own). It opens no network port, runs as your user, keeps agents alive across disconnects, and updates with Studio.

Running work on a machine

The "+" menu gets a Where choice. Free RAM and load are shown so the pick is informed. Agents use the sign-in that lives on that machine; Studio never copies your logins there by itself.

For Cora, the manager stays here (light, holds your memory and logins) and workers run there (heavy: builds, tests, installs). Results come back as git commits and go through the same review as any worker.

Sandboxes

A throwaway machine for one task: a Docker container on this computer or on a machine, made from a repo and branch. The safe place for untrusted pull requests and "let the agent run with full permissions". Limited CPU and RAM, no host mounts, no Docker socket inside, no logins unless you opt in.

Security: what a machine can do to this computer

A connected machine canA connected machine can never
Show output in its own panes (clipboard writes only from a pane you are typing in; never read your clipboard)Read or write files on this computer
Serve pages through forwarded ports (opened in their own browser partition)Open terminals on this computer, or in your other workspaces without asking
Report worker results and hook events with its machine tokenTouch your logins, accounts or Codara settings
Hand back git commits, which you review like any worker'sGet the full agent socket token, or SSH agent forwarding

If a home machine is hacked, the attacker gets that machine and the agent sign-ins stored on it. That is why Studio never copies your logins to machines: the damage stays one machine. They can send fake worker reports, which is why results come back as commits through review, and why a machine marked Shared never gets auto-merge. Removing a machine kills its token and forgets its key in one click. On a home server, a dedicated codara user keeps agents away from your other files.

Decided (25 Oct 2026)

Build phases 1 and 2 now

Agents on an SSH host, then the Machines list, each as its own PR against Cora, behind the machines preference until phase 2 ships.

Your own machines are free for every Studio user

They connect over the LAN, Tailscale or plain SSH, so Codara carries no traffic. Per-task Cloud sandboxes are decided later.

Machines behind NAT: Tailscale and SSH only for now

Relay pairing stays a later option. It could run on Codara Cloud, which has large unused egress (Hetzner includes 20 TB per server, then 1 EUR per TB).
